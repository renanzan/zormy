# Tips and Best Practices

Guide with practical tips to use Zormy efficiently and avoid common issues.

## Code Organization

<Callout type="tip" emoji="💡">
	Zormy benefits from a structure that reflects the layers of [Form Design](/docs/form-design):
	atoms (primitive fields), molecules (groups), organisms (forms/sections), and templates (wizards).
	Organize folders and exports to maximize reusability.
</Callout>

### Recommended project structure

A way to organize the project in a **contextual** manner aligned with Zormy:

```
src/
  fields/                    # Atoms and molecules
    base/                    # Abstract fields (reusable templates)
      TextField.tsx          # abstractField() for text
      SelectField.tsx        # abstractField() for select
      CheckboxField.tsx
    user/
      NameField.tsx          # BaseTextField.extend({ key: "name", schema: ... })
      EmailField.tsx
      PasswordField.tsx
    address/                 # Molecule: group of fields that always appear together
      AddressFields.tsx      # export { StreetField, CityField, ZipField } + optionally <AddressSection />
      index.ts               # re-export to import from a single place
  forms/                     # Organisms: complete forms
    login.tsx
    register.tsx
    contact.tsx
  wizards/                   # Templates and wizard pages
    checkout/
      config.ts              # createWizardConfig({ steps, fields })
      CheckoutWizard.tsx     # useWizard + Wizard + Step (page)
    onboarding/
      config.ts
      OnboardingWizard.tsx
```

**Why this structure?**

- **`fields/base/`** — **Abstract** fields (`abstractField()`) defined once; in other files you only call `.extend({ key, schema? })`. Makes it easier to maintain consistent UI and base validation.
- **`fields/user/`, `fields/address/`** — **Concrete** fields by domain. Molecules such as address can export multiple fields + a section component that renders them together.
- **`forms/`** — Each file assembles a form: array of fields + `<Form>` (or `useZormy`) + page UI. Reuses fields from `fields/`.
- **`wizards/`** — By flow: `config.ts` with `createWizardConfig` (outside the component) and the wizard component that uses `useWizard` and renders `<Wizard>` + `<Step>`.

### Abstract fields (reusable atoms)

Use **`abstractField()`** when multiple fields share the same type and UI, changing only the key (and sometimes the schema):

```tsx
// fields/base/TextField.tsx
import { z } from "zod";
import { abstractField } from "zormy";

export const BaseTextField = abstractField()
	.schema(z.string())
	.render(({ register, fieldState }) => (
		<div>
			<label>{/* can come from props if using .props() */}</label>
			<input {...register()} />
			{fieldState.error && <span className="error">{fieldState.error.message}</span>}
		</div>
	));

// fields/user/NameField.tsx
export const NameField = BaseTextField.extend({
	key: "name",
	schema: z.string().min(3, "Name must have at least 3 characters"),
});

// fields/user/EmailField.tsx
export const EmailField = BaseTextField.extend({
	key: "email",
	schema: z.string().email("Invalid email"),
});
```

This way, any change in the “text” layout or behavior (label, error, accessibility) is made in a single place.

### Molecules: groups of complex fields

For blocks that **always appear together** (e.g., address), define each subfield as an atom and export the set — and optionally a section component that renders them:

```tsx
// fields/address/AddressFields.tsx
import { z } from "zod";
import { field } from "zormy";

export const StreetField = field("address.street")
	.schema(z.string().min(1, "Street is required"))
	.render(({ register, fieldState }) => (
		<div>
			<label>Street</label>
			<input {...register()} />
			{fieldState.error && <span>{fieldState.error.message}</span>}
		</div>
	));

export const CityField = field("address.city")
	.schema(z.string().min(1, "City is required"))
	.render(({ register, fieldState }) => (
		<div>
			<label>City</label>
			<input {...register()} />
			{fieldState.error && <span>{fieldState.error.message}</span>}
		</div>
	));

export const ZipField = field("address.zip")
	.schema(z.string().regex(/^\d{5}-?\d{3}$/, "Invalid ZIP code"))
	.render(({ register, fieldState }) => (
		<div>
			<label>ZIP Code</label>
			<input {...register()} />
			{fieldState.error && <span>{fieldState.error.message}</span>}
		</div>
	));

// Optional: section component to use in forms/wizards
export function AddressSection() {
	return (
		<fieldset>
			<legend>Address</legend>
			<StreetField />
			<CityField />
			<ZipField />
		</fieldset>
	);
}
```

In forms or wizard steps, use the array `[StreetField, CityField, ZipField]` in the resolver and render `<AddressSection />` (or the three separate fields). The fields remain atoms for Zormy; the “molecule” is UI organization and composition.

### When to use `field()` vs `abstractField()`

| Situation                                                           | Use                                                                          |
| ------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| Single, specific field (e.g., "accept terms")                       | `field("acceptTerms").schema(...).render(...)`                               |
| Multiple fields with same UI and type (name, email, description)    | `abstractField().schema(...).render(...)` + `.extend({ key })` for each      |
| Group of fields that always come together (address, phone with DDD) | Multiple `field("...")` in the same file + export array or section component |
| Schema or UI depends on another field                               | `field("...").dependsOn(OtherField).schema((formValues) => ...).render(...)` |

### Feature-based structure (alternative)

If the app is organized **by feature** instead of by type (fields/forms/wizards), you can keep the same idea inside each feature:

```
src/
  features/
    auth/
      fields/
        EmailField.tsx
        PasswordField.tsx
      LoginForm.tsx
      RegisterForm.tsx
    checkout/
      fields/
        AddressFields.tsx
        PaymentFields.tsx
      checkoutWizardConfig.ts
      CheckoutWizard.tsx
  shared/
    fields/
      base/
        TextField.tsx
        SelectField.tsx
```

**Shared** fields (name, email, address used in more than one feature) stay in `shared/fields/` or a root `fields/` module; **feature-specific** fields stay inside the feature folder. The key point: a field defined once is imported and reused in forms and wizards, without duplicating schema or UI.

### Real-Time Validation

Configure the appropriate validation mode:

```tsx
// Immediate validation (better UX)
const form = useForm({
	resolver: zormyResolver({ fields: [NameField] }),
	mode: "onChange", // Validates on every change
});

// Validation on blur (better performance)
const form = useForm({
	resolver: zormyResolver({ fields: [NameField] }),
	mode: "onBlur", // Validates when leaving the field
});
```

## Wizards

<Callout type="info">Split complex forms into smaller steps to improve user experience</Callout>

### Conditional Steps

Use `shouldIncludeStep` for steps that appear conditionally:

```tsx
const wizard = useWizard({
	steps: ["personal", "address", "payment"],
	fields: {
		/* ... */
	},
	shouldIncludeStep: (step, formValues) => {
		if (step === "address") {
			return formValues.needsShipping === true;
		}
		return true;
	},
});
```

### Auto Save

Implement auto save for long forms:

```tsx
const wizard = useWizard({
	steps: ["step1", "step2", "step3"],
	fields: {
		/* ... */
	},
	autoSave: async ({ step, validChangedData }) => {
		await saveToServer(step, validChangedData);
	},
});
```

## Performance

### Lazy Loading Fields

Load heavy fields only when necessary:

```tsx
const HeavyField = field("heavy")
	.schema(z.string())
	.render(({ register }) => {
		// Heavy component loaded only when necessary
		const HeavyComponent = lazy(() => import("./HeavyComponent"));
		return (
			<Suspense fallback={<div>Loading...</div>}>
				<HeavyComponent {...register()} />
			</Suspense>
		);
	});
```

### Memoization

Components returned by `field(...).schema(...).render(...)` already have a stable reference. To wrap with `React.memo` (for example, to avoid parent re-renders), use the already built component:

```tsx
const NameField = field("name")
	.schema(z.string())
	.render(({ register }) => <input {...register()} />);

const MemoizedNameField = React.memo(NameField);
```

### Automated rerender tests

Zormy includes automated tests that ensure **updates in one field do not trigger mass re-renders in independent fields**. These tests create large forms (with dozens of fields) and simulate multiple updates in a single field, verifying that:

- only the updated field (and its direct dependents) are impacted;
- completely unrelated fields keep the same number of renders.

If you add logic that observes the entire form (for example, using `watch()` in many places), consider writing similar tests to ensure you did not introduce unnecessary rerenders.

### Efficiency metrics (re-renders and validation)

Zormy’s performance suite covers two metrics: **number of re-renders** (lifecycle) and **Zod validation execution time**.

- **Re-renders**: tests with **React.Profiler** and `vi.fn()` in `onRender` ensure that, when updating a field, only that field (or the necessary container) re-renders, preserving React Hook Form’s uncontrolled behavior. There is also a stress test with **1000 fields** and `setValue` on the first and last fields to detect scalability degradation.
- **Validation**: **Vitest Benchmark mode** (`pnpm test:bench`) runs the resolver (zormyResolver) at scale and measures _Execution Time_ and _Ops/sec_ to evaluate Zod’s cost in the library.
- **Diagnostics**: if numbers are high, use **React Render Tracker** to analyze the dependency graph and identify where re-renders “leak” (for example, a resolver validating the entire form and causing many inputs to re-render).

Details in `packages/zormy/__tests__/performance/README.md`.

## TypeScript

<Callout type="info">
	Type inference is usually sufficient. Use explicit types when you need to expose the field type in
	APIs or for better documentation.
</Callout>

### Explicit Types (optional)

```tsx
// ✅ Automatic inference (recommended in most cases)
const NameField = field("name")
	.schema(z.string())
	.render(({ register }) => <input {...register()} />);

// ✅ Explicit type (useful to export or document the field API)
const NameField: FieldComponent<"name", z.ZodString> = field("name")
	.schema(z.string())
	.render(({ register }) => <input {...register()} />);
```

### Type Inference

Take advantage of automatic TypeScript inference:

```tsx
// The type is inferred automatically
const form = useForm({
	resolver: zormyResolver({ fields: [NameField, EmailField] }),
	defaultValues: { name: "", email: "" },
});

// form.watch() returns the correct type
const values = form.watch(); // { name: string, email: string }
```

## Debugging

### Useful Logs

```tsx
const form = useForm({
	resolver: zormyResolver({ fields: [NameField] }),
	defaultValues: { name: "" },
});

// View current values
console.log("Values:", form.getValues());

// View errors
console.log("Errors:", form.formState.errors);

// View field state (inside field render)
const NameField = field("name")
	.schema(z.string())
	.render(({ register, fieldState }) => {
		console.log("Field state:", fieldState);
		return <input {...register()} />;
	});
```

## Common Mistakes

<Callout type="error">Avoid these common mistakes when using Zormy</Callout>

### 1. Forgetting to use Form or FormProvider

```tsx
// ❌ Error: fields will not work
<form>
  <NameField />
</form>

// ✅ Correct - using Form (recommended)
<Form methods={form}>
  <NameField />
</Form>

// ✅ Correct - using FormProvider directly
<FormProvider {...form}>
  <form>
    <NameField />
  </form>
</FormProvider>
```

### 2. Incorrect field keys

```tsx
// ❌ Error: key does not match defaultValues
const NameField = field("userName");
const form = useForm({
	defaultValues: { name: "" }, // Should be userName
});

// ✅ Correct
const NameField = field("name");
const form = useForm({
	defaultValues: { name: "" },
});
```

### 3. Unconfigured dependencies

```tsx
// ❌ Error: field will not be revalidated when dependency changes
const PasswordField = field("password").schema((formValues) => {
	// Uses formValues.hasPassword but does not declare dependency
});

// ✅ Correct
const PasswordField = field("password")
	.dependsOn(HasPasswordField)
	.schema((formValues) => {
		// Will now be revalidated when HasPasswordField changes
	});
```
