# Dicas e Boas Práticas

Guia com dicas práticas para usar o Zormy de forma eficiente e evitar problemas comuns.

## Organização de Código

<Callout type="tip" emoji="💡">
	O Zormy se beneficia de uma estrutura que reflita as camadas de [Design de
	formulários](/docs/form-design): átomos (campos primitivos), moléculas (grupos), organismos
	(formulários/seções) e templates (wizards). Organize pastas e exports para aproveitar ao máximo a
	reutilização.
</Callout>

### Estrutura de projeto recomendada

Uma forma de organizar o projeto de forma **contextual** e alinhada ao Zormy:

```
src/
  fields/                    # Átomos e moléculas
    base/                    # Campos abstratos (templates reutilizáveis)
      TextField.tsx          # abstractField() para texto
      SelectField.tsx        # abstractField() para select
      CheckboxField.tsx
    user/
      NameField.tsx          # BaseTextField.extend({ key: "name", schema: ... })
      EmailField.tsx
      PasswordField.tsx
    address/                 # Molécula: grupo de campos que sempre aparecem juntos
      AddressFields.tsx      # export { StreetField, CityField, ZipField } + opcionalmente <AddressSection />
      index.ts               # re-export para importar de um único lugar
  forms/                     # Organismos: formulários completos
    login.tsx
    register.tsx
    contact.tsx
  wizards/                   # Templates e páginas de wizard
    checkout/
      config.ts              # createWizardConfig({ steps, fields })
      CheckoutWizard.tsx     # useWizard + Wizard + Step (página)
    onboarding/
      config.ts
      OnboardingWizard.tsx
```

**Por que essa estrutura?**

- **`fields/base/`** — Campos **abstratos** (`abstractField()`) definidos uma vez; em outros arquivos você só faz `.extend({ key, schema? })`. Facilita manter consistência de UI e validação base.
- **`fields/user/`, `fields/address/`** — Campos **concretos** por domínio. Moléculas como endereço podem exportar vários campos + um componente de seção que os renderiza juntos.
- **`forms/`** — Cada arquivo monta um formulário: array de campos + `<Form>` (ou `useZormy`) + UI da página. Reutiliza campos de `fields/`.
- **`wizards/`** — Por fluxo: `config.ts` com `createWizardConfig` (fora do componente) e o componente do wizard que usa `useWizard` e renderiza `<Wizard>` + `<Step>`.

### Campos abstratos (átomos reutilizáveis)

Use **`abstractField()`** quando vários campos compartilham o mesmo tipo e a mesma UI, mudando só a chave (e às vezes o schema):

```tsx
// fields/base/TextField.tsx
import { z } from "zod";
import { abstractField } from "zormy";

export const BaseTextField = abstractField()
	.schema(z.string())
	.render(({ register, fieldState }) => (
		<div>
			<label>{/* pode vir de props se usar .props() */}</label>
			<input {...register()} />
			{fieldState.error && <span className="error">{fieldState.error.message}</span>}
		</div>
	));

// fields/user/NameField.tsx
export const NameField = BaseTextField.extend({
	key: "name",
	schema: z.string().min(3, "Nome deve ter pelo menos 3 caracteres"),
});

// fields/user/EmailField.tsx
export const EmailField = BaseTextField.extend({
	key: "email",
	schema: z.string().email("E-mail inválido"),
});
```

Assim, qualquer mudança no layout ou comportamento do “texto” (label, erro, acessibilidade) é feita em um único lugar.

### Moléculas: grupos de campos complexos

Para blocos que **sempre aparecem juntos** (ex.: endereço), defina cada subcampo como átomo e exporte o conjunto — e opcionalmente um componente de seção que os renderiza:

```tsx
// fields/address/AddressFields.tsx
import { z } from "zod";
import { field } from "zormy";

export const StreetField = field("address.street")
	.schema(z.string().min(1, "Rua obrigatória"))
	.render(({ register, fieldState }) => (
		<div>
			<label>Rua</label>
			<input {...register()} />
			{fieldState.error && <span>{fieldState.error.message}</span>}
		</div>
	));

export const CityField = field("address.city")
	.schema(z.string().min(1, "Cidade obrigatória"))
	.render(({ register, fieldState }) => (
		<div>
			<label>Cidade</label>
			<input {...register()} />
			{fieldState.error && <span>{fieldState.error.message}</span>}
		</div>
	));

export const ZipField = field("address.zip")
	.schema(z.string().regex(/^\d{5}-?\d{3}$/, "CEP inválido"))
	.render(({ register, fieldState }) => (
		<div>
			<label>CEP</label>
			<input {...register()} />
			{fieldState.error && <span>{fieldState.error.message}</span>}
		</div>
	));

// Opcional: componente de seção para usar em formulários/wizards
export function AddressSection() {
	return (
		<fieldset>
			<legend>Endereço</legend>
			<StreetField />
			<CityField />
			<ZipField />
		</fieldset>
	);
}
```

Nos formulários ou steps do wizard, use o array `[StreetField, CityField, ZipField]` no resolver e renderize `<AddressSection />` (ou os três campos soltos). Os campos continuam sendo átomos para o Zormy; a “molécula” é organização e composição na UI.

### Quando usar `field()` vs `abstractField()`

| Situação                                                           | Use                                                                             |
| ------------------------------------------------------------------ | ------------------------------------------------------------------------------- |
| Campo único, específico (ex.: "aceito termos")                     | `field("acceptTerms").schema(...).render(...)`                                  |
| Vários campos com mesma UI e tipo (nome, e-mail, descrição)        | `abstractField().schema(...).render(...)` + `.extend({ key })` em cada um       |
| Grupo de campos que sempre vêm juntos (endereço, telefone com DDD) | Vários `field("...")` no mesmo arquivo + export de array ou componente de seção |
| Schema ou UI depende de outro campo                                | `field("...").dependsOn(OutroCampo).schema((formValues) => ...).render(...)`    |

### Estrutura por feature (alternativa)

Se o app for organizado **por feature** em vez de por tipo (fields/forms/wizards), você pode manter a mesma ideia dentro de cada feature:

```
src/
  features/
    auth/
      fields/
        EmailField.tsx
        PasswordField.tsx
      LoginForm.tsx
      RegisterForm.tsx
    checkout/
      fields/
        AddressFields.tsx
        PaymentFields.tsx
      checkoutWizardConfig.ts
      CheckoutWizard.tsx
  shared/
    fields/
      base/
        TextField.tsx
        SelectField.tsx
```

Campos **compartilhados** (nome, e-mail, endereço usado em mais de uma feature) ficam em `shared/fields/` ou em um módulo `fields/` na raiz; campos **específicos** da feature ficam dentro da pasta da feature. O importante é: um campo definido uma vez é importado e reutilizado nos formulários e wizards, sem duplicar schema nem UI.

### Validação em Tempo Real

Configure o modo de validação apropriado:

```tsx
// Validação imediata (melhor UX)
const form = useForm({
	resolver: zormyResolver({ fields: [NameField] }),
	mode: "onChange", // Valida em cada mudança
});

// Validação ao sair do campo (melhor performance)
const form = useForm({
	resolver: zormyResolver({ fields: [NameField] }),
	mode: "onBlur", // Valida ao sair do campo
});
```

## Wizards

<Callout type="info">
	Divida formulários complexos em steps menores para melhorar a experiência do usuário
</Callout>

### Steps Condicionais

Use `shouldIncludeStep` para steps que aparecem condicionalmente:

```tsx
const wizard = useWizard({
	steps: ["personal", "address", "payment"],
	fields: {
		/* ... */
	},
	shouldIncludeStep: (step, formValues) => {
		if (step === "address") {
			return formValues.needsShipping === true;
		}
		return true;
	},
});
```

### Auto Save

Implemente auto save para formulários longos:

```tsx
const wizard = useWizard({
	steps: ["step1", "step2", "step3"],
	fields: {
		/* ... */
	},
	autoSave: async ({ step, validChangedData }) => {
		await saveToServer(step, validChangedData);
	},
});
```

## Performance

### Lazy Loading de Campos

Carregue campos pesados apenas quando necessário:

```tsx
const HeavyField = field("heavy")
	.schema(z.string())
	.render(({ register }) => {
		// Componente pesado carregado apenas quando necessário
		const HeavyComponent = lazy(() => import("./HeavyComponent"));
		return (
			<Suspense fallback={<div>Carregando...</div>}>
				<HeavyComponent {...register()} />
			</Suspense>
		);
	});
```

### Memoização

Os componentes retornados por `field(...).schema(...).render(...)` já têm referência estável. Para envolver em `React.memo` (por exemplo, para evitar re-renders do pai), use o componente já construído:

```tsx
const NameField = field("name")
	.schema(z.string())
	.render(({ register }) => <input {...register()} />);

const MemoizedNameField = React.memo(NameField);
```

### Testes automatizados de rerender

O Zormy possui testes automatizados que garantem que **updates em um campo não disparem re-renders em massa em campos independentes**. Esses testes criam formulários grandes (com dezenas de campos) e simulam várias atualizações em um único campo, verificando que:

- apenas o campo atualizado (e seus dependentes diretos) são impactados;
- campos totalmente irrelevantes mantêm o mesmo número de renderizações.

Se você adicionar lógica que observe o formulário inteiro (por exemplo, usando `watch()` em muitos lugares), considere escrever testes semelhantes para garantir que não introduziu rerenders desnecessários.

### Métricas de eficiência (re-renders e validação)

A suíte de performance do Zormy cobre duas métricas: **quantidade de re-renders** (ciclo de vida) e **tempo de execução da validação Zod**.

- **Re-renders**: testes com **React.Profiler** e `vi.fn()` em `onRender` garantem que, ao atualizar um campo, apenas aquele campo (ou o container necessário) re-renderize, preservando o comportamento uncontrolled do React Hook Form. Há também um teste de estresse com **1000 campos** e `setValue` no primeiro e no último para detectar degradação de escalabilidade.
- **Validação**: o modo **Benchmark do Vitest** (`pnpm test:bench`) executa o resolver (zormyResolver) em massa e mede _Execution Time_ e _Ops/sec_, para avaliar o custo do Zod na lib.
- **Diagnóstico**: se os números estiverem altos, use o **React Render Tracker** para analisar o grafo de dependências e identificar onde os re-renders "vazam" (por exemplo, resolver validando o formulário inteiro e causando re-render em muitos inputs).

Detalhes em `packages/zormy/__tests__/performance/README.md`.

## TypeScript

<Callout type="info">
	A inferência de tipos costuma ser suficiente. Use tipos explícitos quando precisar expor o tipo do
	campo em APIs ou para melhor documentação.
</Callout>

### Tipos Explícitos (opcional)

```tsx
// ✅ Inferência automática (recomendado na maioria dos casos)
const NameField = field("name")
	.schema(z.string())
	.render(({ register }) => <input {...register()} />);

// ✅ Tipo explícito (útil para exportar ou documentar a API do campo)
const NameField: FieldComponent<"name", z.ZodString> = field("name")
	.schema(z.string())
	.render(({ register }) => <input {...register()} />);
```

### Inferência de Tipos

Aproveite a inferência automática do TypeScript:

```tsx
// O tipo é inferido automaticamente
const form = useForm({
	resolver: zormyResolver({ fields: [NameField, EmailField] }),
	defaultValues: { name: "", email: "" },
});

// form.watch() retorna o tipo correto
const values = form.watch(); // { name: string, email: string }
```

## Erros Comuns

<Callout type="error">Evite esses erros comuns ao usar Zormy</Callout>

### 1. Esquecer de usar Form ou FormProvider

```tsx
// ❌ Erro: campos não funcionarão
<form>
  <NameField />
</form>

// ✅ Correto - usando Form (recomendado)
<Form methods={form}>
  <NameField />
</Form>

// ✅ Correto - usando FormProvider diretamente
<FormProvider {...form}>
  <form>
    <NameField />
  </form>
</FormProvider>
```

### 2. Chaves de campos incorretas

```tsx
// ❌ Erro: chave não corresponde ao defaultValues
const NameField = field("userName");
const form = useForm({
	defaultValues: { name: "" }, // Deveria ser userName
});

// ✅ Correto
const NameField = field("name");
const form = useForm({
	defaultValues: { name: "" },
});
```

### 3. Dependências não configuradas

```tsx
// ❌ Erro: campo não será revalidado quando dependência mudar
const PasswordField = field("password").schema((formValues) => {
	// Usa formValues.hasPassword mas não declara dependência
});

// ✅ Correto
const PasswordField = field("password")
	.dependsOn(HasPasswordField)
	.schema((formValues) => {
		// Agora será revalidado quando HasPasswordField mudar
	});
```
